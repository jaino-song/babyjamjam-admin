# 실환경 오류 검증 실행 절차와 증거 기록 양식

기준: [BJJ-319 실행 계획](plans/bjj-319-remaining-plan.md) Phase 10 (Task 10.1). 연결: [Error Management v1.0 적용 현황](error-management.md), BJJ-317 Sentry 운영 항목, [ADR-006](adr/ADR-006-sentry-driven-db-route-failover.md), [ADR-008](adr/ADR-008-sentry-host-failover-controller.md).

이 문서는 **나중에 실행할** 실환경 검증의 절차와 증거 양식을 준비한 것이다. 이 문서의 작성·병합은 실환경 실행 승인이 아니며, 승인 값이 채워지고 별도 승인이 기록되기 전까지 아래 절차를 실행하지 않는다. 빈칸(`____`)은 승인 시점에 실제 값으로 채우고, 실행 전까지 임의 값을 발명하지 않는다.

## 1. 승인 gate

- 실환경 실행(외부 접수·발송·서명·실제 Sentry 수신 유발)은 **main이 별도로 명시적 사용자 승인을 받은 뒤에만** 수행한다. Phase close gate도 "문서 감사 이후 main이 실제 실행 승인과 테스트 대상을 확인"하는 것을 요구한다.
- 이 문서의 존재, 병합, 감사 통과는 실행 권한의 증거가 아니다. 계획의 계획 검토 기록과 동일하게 "승인된 실환경 작업"과 "준비된 절차"는 구분한다.
- 승인 기록은 §7 증거 양식의 첫 행(승인 자체)으로 남긴다. 승인일·승인자·승인 범위가 비어 있으면 절차를 시작하지 않는다.

### 고정 중지 조건 (값과 무관하게 항상 적용)

다음 중 하나가 관찰되면 즉시 실행을 중단하고 §4의 상태 확인만 수행한 뒤 main에 보고한다:

1. 승인 목록 밖의 수신자·지점·고객에게 부수 효과가 발생한 흔적.
2. `GET /health/ready`가 503을 반환하거나, DB route 관련 이벤트(`db.route`, `prisma.code` 태그)가 Sentry에 새로 나타날 때. ADR-006의 failover는 Sentry 신호로 시작될 수 있으므로, 실환경 검증은 이 경로를 유발해서는 안 된다.
3. ADR-008의 failover controller가 armed 상태로 관찰될 때 (현재 기준: 미설치·미활성). 이 상태에서는 문서 발송·서명 시나리오를 실행하지 않는다.
4. 동일 요청의 응답을 두 번 받았거나(중복 접수 의심), UNKNOWN/PARTIALLY_APPLIED가 승인 시나리오 밖에서 관찰될 때.

## 3. Read-only 확인 우선 순서

실행 순서는 항상 "읽기 → 상태 확인 → 최소 실제 행동"이다. 어떤 단계든 앞 단계 증거 없이 다음 단계로 가지 않는다.

### 3.0 단계별 증거 형식 (모든 단계 공통)

각 단계가 끝날 때마다 §7 양식에 한 행을 남긴다. 한 행의 최소 필드:

| 필드 | 의미 |
| --- | --- |
| 일시 (timestamp) | 관찰 시각 (KST, Asia/Seoul) |
| 행위자 (actor) | 실행한 사람 또는 명령/화면 |
| 대상 (target) | endpoint·화면·수신자 식별자(마스킹)·Sentry issue 링크 |
| 관찰 (observed) | 실제 응답/값/스크린샷 — 기대 문장을 복사하지 않는다 |
| 판정 (judgment) | 기대와 일치 / 불일치 / 미확정 — 근거 필드를 인용 |

### 3.1 읽기 전용 확인 (실제 행동 0회)

아래를 순서대로 확인하고 각각 증거 행을 남긴다. 실패 시 이후 단계를 실행하지 않는다.

1. `GET /health` — 프로세스 생존 확인 (DB 독립, ADR-006).
2. `GET /health/ready` — 200이면 통과. 503이면 중지 (detail-free 응답인 것 자체가 관찰 사항이다).
3. 대상 환경의 배포 SHA가 §2 표와 일치하는지 확인.
4. Sentry 프로젝트 접근 권한과 대상 환경(`dev`/`preview`/`production`) 라벨 확인 — 수신 경로가 열려 있는지의 확인이며 보존기간·알림 설정은 BJJ-317 소유라 여기서 판정하지 않는다.
5. ADR-008 failover controller가 대상 범위에 없음을 확인 (미설치·disarmed).
6. 이력·로그 조회 화면/endpoint에서 §2 대상 지점의 기존 데이터 상태를 기록해 둔다 (정리 단계의 비교 기준).

### 3.2 상태 확인 우선 원칙

- 결과가 불명확하면(UNKNOWN, PARTIALLY_APPLIED, 타임아웃, 창 닫힘) 재실행이 아니라 상태 확인이 우선이다. 새 오류 처리 계층은 자동 재시도를 하지 않으며, `CHECK_STATUS`는 정보이고 임의 URL/코드를 실행하지 않는다.
- 상태 확인은 읽기 조회(발송 로그, 문서 작업 상태, 문서 이력)로 수행하고, 그 결과로 다음 행동을 결정한다. 상태 확인조차 불명확하면 해당 시나리오는 미확정으로 기록하고 main에 보고한다.

### 3.3 최소 실제 행동 원칙

- 승인된 시나리오 1건당 필요한 최소 요청만 보낸다. 같은 시나리오의 반복 재현은 중지 조건의 횟수 상한 안에서만 하고, 각 반복도 개별 증거 행으로 남긴다.
- 응답 본문을 통째로 기록하지 않는다. 요청 ID(`X-Request-Id` 헤더 또는 problem+json 본문의 `requestId`)와 공개 필드만 기록한다.

## 4. 시나리오 절차

계획의 필수 검증 시나리오 중 실환경 대상 5가지다. 각 시나리오는 준비 → 실행 → 관찰 → 중지 → 정리 순서이며, "입증 항목"은 어떤 등록 코드/outcome이 관찰되어야 그 시나리오의 증거가 되는지를 말한다. 관찰값이 입증 항목과 달라도 그대로 기록한다 — 지우거나 기대에 맞춰 고쳐 쓰지 않는다.

공통 준비(각 시나리오 앞에 1회): §3.1 읽기 전용 확인이 모두 통과했고, §2 값이 채워져 있으며, 대상 지점의 정리 전 상태가 §3.1-6에 기록돼 있다.

### S1. 고객 등록 성공·발송 실패

계획 표 기대: 고객 1건 보존, 실패 단계 구분, 전체 재실행으로 고객/문자 중복 없음.

- **준비:** 고객 등록에 사용할 테스트 입력(연락처는 지정 수신자)을 승인 시점에 확정한다. 발송 실패 단계를 관찰할 경로(등록 환영 트리거의 발송 로그, 또는 승인된 문자 화면 1건)를 §2에 기록해 둔다. 제공자 장애 주입 등 실패 강제 방법은 승인 없이 실행하지 않는다 — 자연 관찰이 불가능하면 이 시나리오의 발송 실패 절반은 미실시로 기록한다.
- **실행:** (a) 고객 1건을 등록한다. (b) 등록 직후의 발송 상태를 발송 로그에서 조회한다 (수정·재제출 없이). (c) 승인된 범위 내에서 같은 연락처로 등록을 한 번 더 시도한다.
- **관찰:** 고객 목록에 신규 고객이 정확히 1건인지, 발송 로그 상태(pending/sent/failed 및 provider 접수 상태)가 단계별로 구분되는지, 두 번째 등록 시도의 응답 코드, 발송 로그에 문자 중복 행이 없는지.
- **중지:** 등록 응답이 두 번 성공하거나(중복 생성), 발송 로그가 같은 수신자에 2행 이상 생기면 중지.
- **정리:** 테스트 고객을 삭제 가능 여부 확인 후 삭제하거나 보존을 기록한다. 발송 로그·트리거 상태는 잔존 여부를 기록한다.
- **입증 항목:** 두 번째 등록 거절 = `CLIENT_PHONE_ALREADY_REGISTERED` (409). 발송 실패 단계 = message-delivery 등록 코드 체계의 outcome으로 관찰: 미시작 거절 `NOT_APPLIED`(`MESSAGE_SEND_NOT_STARTED`, 503), 접수 불명 `UNKNOWN`(`MESSAGE_SEND_UNCONFIRMED`, 502) — 단, 환영 트리거 경로에서 이 코드가 화면 노출되지 않으면 로그 상태값으로 관찰하고 그 사실을 기록한다. UNKNOWN 관찰 시 재제출 없이 상태 확인으로 종결.

### S2. provider 접수 후 응답 유실·결과 저장 실패

계획 표 기대: UNKNOWN과 상태 확인, 자동 재발송 없음.

- **준비:** 유실은 자연 발생을 기다리거나 승인된 재현 방법이 있을 때만 만든다. 네트워크 차단·프록시 장애 주입 같은 강제 방법은 별도 승인 없이 실행하지 않는다. 승인 시점에 "자연 관찰만 / 승인된 강제 방법 있음" 중 무엇인지 §2에 기록한다. 관찰 경로: 문자는 발송 로그의 provider 접수 상태, 문서는 dispatch/finalize 작업 상태와 envelope 응답.
- **실행:** 승인된 문자 1건(또는 문서 1건)을 발송하고, 응답이 불명확하게 끝나는 순간까지 화면을 닫거나 새로고침하지 않고 관찰한다. 강제 재현이 승인된 경우에만 그 방법을 적용한다.
- **관찰:** 화면 안내 문구(상태 확인 안내), 이후 수동 상태 조회 결과, 동일 요청의 자동 재발송 흔적(발송 로그 행 수, provider 접수 건수)이 일정 시간(§2 상한 내) 동안 없는지.
- **중지:** 재발송 흔적이 관찰되면 즉시 중지 — 이는 계획 위반이며 결함 기록 대상이다.
- **정리:** 해당 수신자의 발송 로그를 보존하고, 불명확 상태가 해소됐는지 이후 조회로 확인해 보고에 첨부한다.
- **입증 항목:** 문자 `MESSAGE_SEND_UNCONFIRMED`(502, `UNKNOWN` + `CHECK_STATUS`), 문서 발송 `DISPATCH_UNCERTAIN`(502, `UNKNOWN` + `CHECK_STATUS`), 로컬 저장 실패 `DOCUMENT_LOCAL_PERSIST_FAILED`(502, `PARTIALLY_APPLIED` + `CHECK_STATUS`), 원격 미확인 `REMOTE_DOCUMENT_UNCONFIRMED`(502, `UNKNOWN` + `CHECK_STATUS`). 자동 재시도 없음은 recovery.retry.mode `NEVER`와 발송 로그 행 수 1행으로 함께 입증한다.

### S3. 부분 발송

계획 표 기대: 부분 접수 상태 영속 보존, 전체 수신자 재발송 금지.

- **준비:** 수신자 2인 이상(모두 승인 목록 내)과 일부 실패가 관찰 가능한 조건을 승인 시점에 확정한다. 부분 접수 영속성 확인에 쓸 조회 경로(재시작 뒤 재조회 포함)를 미리 정한다.
- **실행:** 승인된 수신자 집합에 1회 발송한다. (선택, 승인 시) 프로세스 재시작 후 같은 발송 건의 상태를 재조회해 fence가 남아 있는지 확인한다.
- **관찰:** 접수 성공/실패 수신자별 구분, 부분 접수 상태의 응답 코드와 outcome, 같은 발송 건 전체(성공 수신자 포함) 재발송 시도의 응답, 시간 경과 후(§2 상한) 상태가 보존돼 있는지.
- **중지:** 성공 수신자에게 재발송이 일어나거나 부분 상태가 조회에서 사라지면 중지 — 결함 기록 대상이다.
- **정리:** 수신자별 결과 표를 §7에 첨부하고, 실패 수신자의 재처리 여부는 승인자와 별도로 결정한다 (이 절차가 자동 처리를 보장하지 않는다).
- **입증 항목:** `MESSAGE_SEND_PARTIAL`(502, `PARTIALLY_APPLIED` + `CHECK_STATUS`)과 부분 접수 fence의 영속 조회. 전체 재발송 금지는 재시도 응답이 등록 코드로 거절되는 것으로 입증한다 — 이미 진행 중인 요청의 중복은 `MESSAGE_SEND_ALREADY_REQUESTED`(409, `UNKNOWN` + `CHECK_STATUS`)로 관찰되며, 그 외 거절의 실제 관찰값을 증거 행에 기록한다 (이 문서에서 미리 특정하지 않는다).

### S4. 서명된 계약 수정·iframe 종료

계획 표 기대: 기존 문서 이력 유지, 불명확한 결과 재실행 금지.

- **준비:** 서명 대상 테스트 계약과 서명자(지정 수신자)를 승인 시점에 확정한다. iframe/서명 창을 닫는 시점(제출 전·후 각 1회 이상)을 미리 정한다. eformsign 문서 이력 조회 경로를 확인해 둔다.
- **실행:** (a) 문서 발송 후 서명 완료 전에 서명 창을 닫는다. (b) 상태를 조회하고, 승인된 범위 안에서만 재시도 가능 여부를 화면 안내대로 따른다. (c) 이미 서명된 계약에 수정을 시도한다.
- **관찰:** iframe 종료 직후 화면 잠금과 안내, 재실행 버튼의 비활성/부재, 문서 이력에 기존 문서가 보존되는지, 서명 완료 문서의 수정 시도 응답 코드, 결과 불명 상태에서의 재발송 시도 응답.
- **중지:** 같은 문서에 발송 기록이 2건 생기거나, 이미 서명된 문서의 이력이 변경되면 중지.
- **정리:** 테스트 계약·문서를 승인된 방법으로 정리하거나 보존을 기록한다. eformsign 측 잔존 문서 유무를 이력 조회로 확인해 기록한다.
- **입증 항목:** 재시도 거절 `DISPATCH_ALREADY_ACCEPTED`(409)·`DOCUMENT_DISPATCH_IN_PROGRESS`(409)·`DUPLICATE_PENDING_DOCUMENT`(409), 서명 후 수정 거절 `CONTRACT_ALREADY_SIGNED`(409), 락 경합 `DOCUMENT_LOCK_UNAVAILABLE`(503)·`DOCUMENT_LOCK_LOST`(409), 종료 미확인 `DOCUMENT_FINALIZE_UNCONFIRMED`(502, `UNKNOWN` + `CHECK_STATUS`)·`REMOTE_DOCUMENT_UNCONFIRMED`(502). headless envelope의 `ok:false` + 등록 코드 + outcome(`NOT_APPLIED`+`NONE` 또는 `UNKNOWN`+`CHECK_STATUS`) 조합으로 판정한다.

### S5. 취소·인증 갱신·만료

계획 표 기대: 기존 인증 정상 동작, 중첩 재시도와 중복 알림 없음.

- **준비:** 테스트 계정의 세션(웹/모바일 각 1)과 재설정 링크 1건을 발급할 수 있는 상태를 확인한다. 네트워크 취소 관찰은 브라우저 개발자 도구의 요청 목록으로 기록한다.
- **실행:** (a) 정상 로그인·조회 1회. (b) 세션 만료(또는 로그아웃) 뒤 보호 화면 접근 — 자동 갱신 1회 후 재시도 1회를 요청 목록에서 센다. (c) 재설정 링크를 만료·재사용 상태로 각 1회씩 사용한다. (d) 요청 진행 중 취소(화면 이동)를 1회 수행한다.
- **관찰:** (b)에서 refresh 요청 수와 재시도 수(기대: 각 1), (c)의 응답 코드, (d) 취소 뒤 중복 알림·토스트 수, 재로그인 정상 동작.
- **중지:** refresh 요청이 연속 2회 초과 관찰되거나, 같은 알림이 중복 표시되면 중지.
- **정리:** 테스트 계정의 세션을 로그아웃으로 정리하고 발급한 재설정 링크의 잔존 여부를 기록한다.
- **입증 항목:** 재설정 링크 만료·재사용·무효 = `AUTH_RESET_TOKEN_EXPIRED`·`AUTH_RESET_TOKEN_USED`·`AUTH_RESET_TOKEN_INVALID`(모두 400). 계정 상태 거절 = `PENDING_APPROVAL`·`ACCOUNT_REJECTED`·`ACCOUNT_PROFILE_INCOMPLETE`·`NO_ACCESSIBLE_BRANCH`(모두 403). 취소·갱신은 코드가 아니라 요청 계수(1회 refresh + 1회 재시도)와 중복 알림 0으로 입증한다.

### 이 시나리오 표의 나머지 행

계획 필수 표의 입력 검증·동시성·테넌트 경계·구버전 호환 행은 이미 통합 테스트와 로컬 검증으로 증거를 남겼고(`docs/error-management.md` Task 9.1 절), 실환경에서 의도적으로 재현하지 않는다(실제 고객을 이용한 장애 재현 비목표). 실환경에서 해당 계열의 결함이 우연히 관찰되면 증거 행으로 남기고 별도 결함 기록으로 넘긴다.

## 5. Sentry 수신 검증 (BJJ-317 연결)

대상: 실제 Sentry 프로젝트로의 수신과 이벤트 내용. 보존기간·알림 정책 자체는 BJJ-317 소유이며 이 절차는 수신 사실과 내용 연결만 판정한다.

### 5.1 검증 항목과 기대

| 항목 | 기대 |
| --- | --- |
| 공개 code/outcome 연결 | 이벤트 태그 `error.code`는 공개 카탈로그 값, `outcome`은 `NOT_APPLIED`/`FAILED`/`PARTIALLY_APPLIED`/`UNKNOWN` 중 하나. 이벤트 contexts의 `requestReference.requestId`가 응답 헤더 `X-Request-Id` 및 problem+json 본문 `requestId`와 동일하다. |
| 중복 capture 0 | 같은 예외 인스턴스는 이벤트 1개 (WeakSet 중복 방지 + 실행 경계별 최종 보고 책임, EM-OBS-03). 같은 원인이 별도 issue로 무한 분리되지 않는다. |
| 민감정보 비노출 | 메시지는 일반 문구("Backend failure" 등), `user` 비어 있음, 요청 `data`/`query_string`/`cookies`/`env` 없음, 헤더는 마스킹, 전화번호·이메일·토큰 패턴이 extras/stacktrace에 없음 (`EM-SEC-01`). |
| 4xx 미보고 (설계된 부재) | 예상 4xx 이벤트는 beforeSend에서 drop된다. "Sentry에 없음"이 이 계열의 기대 증거다 — 부재를 결함으로 기록하지 않는다. |

### 5.2 절차와 명령

1. **수신 경로 확인 (승인된 smoke 이벤트 1건):** backend 디렉터리에서 `pnpm sentry:smoke`를 실행한다. 이 스크립트는 preview 환경 전용(`SENTRY_ENVIRONMENT=preview` 필수, `SENTRY_DSN` 필수)이며 `smoke_test: "true"` 태그와 `operation: auto-finalize`, feature `service-records`로 이벤트 1개를 보내고 flush를 확인한다. 다른 환경에서 이 스크립트를 실행하지 않는다.
2. **Sentry UI에서 smoke 이벤트 탐색:** 필터 `smoke_test:"true"` (필요하면 `feature:service-records`와 조합). 관찰: 태그 `error.code`·`outcome` 유무, contexts `requestReference` 유무, §5.1 비노출 항목 전체. 이 이벤트에는 requestId가 없으므로 `requestReference` 부재는 이 이벤트에 한해 기대와 일치다.
3. **code/outcome/requestReference 연결 (실제 요청 이벤트):** 시나리오 S1~S5 실행 중 5xx 또는 불명확 결과가 발생하면, 그 요청의 응답 `X-Request-Id` 값과 Sentry 이벤트의 `requestReference.requestId`를 대조한다. 이벤트 검색은 Sentry UI 필터로 수행한다: `error.code:"<관찰된 코드>"`, `outcome:"<관찰된 outcome>"`, `feature:backend` (또는 `service-records`). 대조 성적표(두 값의 일치)를 증거 행에 남긴다.
4. **중복 capture 확인:** 동일 요청으로 생긴 issue의 event 수를 센다. 기대: 같은 예외 인스턴스 1개. 시나리오 반복으로 같은 원인이 여러 번 관찰되면 issue 그룹핑 1개 안에 event가 쌓이는지 확인하고, 별도 issue로 분리된 수를 기록한다.
5. **DB failover 경로 비유발 확인:** Sentry에서 태그 `feature:database-failover` 이벤트가 이 절차 중 새로 생기지 않았음을 확인한다 (ADR-006의 failover 트리거 오염 방지). ADR-008의 controller 수신 계약은 미설치·미활성 상태라 유발 대상이 아니다.
6. **기록 위치:** 위 모든 관찰은 §7 양식의 증거 표에 행으로 남긴다. Sentry issue/event 링크(URL)를 증거 칸에 그대로 넣고, 스크린샷은 이벤트 상세(태그·contexts·Request 탭)를 캡처한다. Sentry 프로젝트 식별자(org/project slug)는 §2 승인 시 기입한다.

이 절차가 새 보고 경로를 추가하지 않는다. 기존 실행 경계(`backend/infrastructure/observability/`)와 필터·sanitize 정책을 그대로 관찰한다.

## 6. 중지·정리 공통 절차

- **중지:** §2 고정 중지 조건 또는 시나리오별 중지 조건 충족 시, 진행 중인 요청의 응답을 기다리지 않고 기록 가능한 범위의 관찰만 남긴다. 이후 행동은 §3.2 상태 확인(읽기)만 허용된다.
- **정리:** 시나리오별 정리 절차를 수행하고, §2의 정리 담당자·시한 안에 (a) 테스트 데이터 삭제/보존 상태, (b) 발송·서명 잔존 기록, (c) 비용 실적(승인 상한 대비)을 §7 표에 남긴다. 정리가 시한 내 끝나지 않으면 운영 검증 gate를 닫지 않고 미완료로 기록한다.
