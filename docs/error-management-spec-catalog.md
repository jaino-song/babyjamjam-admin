## 1. 규칙의 강도와 적용 방식

- **EM-GOV-01** *(필수)* — 프로젝트 시작 시 14절의 적용 프로필을 작성한다. 프레임워크, 오류 전달 방식, 지원 언어, 문구 원본, 관측 도구, 재시도 정책을 명시한다.
- **EM-GOV-02** *(필수)* — 각 기능의 명세에 성공 조건뿐 아니라 예상 가능한 실패 조건, 사용자 안내, 실제 처리 상태, 복구 동작을 함께 정의한다.
- **EM-GOV-03** *(필수)* — 변경 시 이 문서의 규칙 ID를 리뷰 근거로 사용할 수 있어야 한다. 예외에는 대상 규칙, 범위, 사유, 대체 안전장치, 책임자와 재검토 시점을 기록한다.
- **EM-GOV-04** *(금지)* — 문서 작성만으로 프로젝트가 규격을 준수한다고 표시하지 않는다. 실제 코드와 테스트의 증거로 준수 상태를 확인한다.

## 2. 오류 모델의 기본 원칙

### 2.1 같은 사건을 세 가지 목적으로 분리한다

- **EM-CORE-01** *(필수)* — 세 모델을 명시적으로 분리한다. 내부 Error 객체를 JSON으로 직렬화하거나, 내부 메시지를 짧게 잘라 사용자 안내로 사용하지 않는다.
- **EM-CORE-02** *(필수)* — 프로그램 분기는 코드 또는 검증된 구조화 필드로 수행한다. 한국어·영어 메시지 비교, 부분 문자열 검색, 정규식으로 업무 원인을 추측하는 처리는 금지한다.
- **EM-CORE-03** *(필수)* — 안내는 확인된 사실만 표현한다. 원인을 모르는데 네트워크 장애, 사용자 실수, 발송 실패, 롤백 완료라고 단정하지 않는다.
- **EM-CORE-04** *(필수)* — 상세함은 사용자가 볼 권한이 있는 업무 정보의 구체성을 의미한다. SQL, 스택, 토큰, 내부 주소의 공개를 의미하지 않는다.
- **EM-CORE-05** *(필수)* — 문구의 구체성은 증거 수준을 넘지 않는다. 연결된 데이터가 있다는 사실만 확인했다면, 이를 진행 중인 계약 3건이라고 구체화하지 않는다.
### 2.2 오류 분류와 책임

- **EM-CORE-06** *(필수)* — 예상 가능성, 운영 심각도, 재시도 가능성, 실제 처리 결과를 별개의 속성으로 판단한다. 업무 오류라고 항상 무시하거나, 5xx라고 항상 재시도하지 않는다.

## 3. 계층별 처리 구조

- **EM-ARCH-01** *(필수)* — 도메인 모델은 HTTP 상태 코드, 토스트, React, Sentry 같은 전송·표시·관측 도구에 의존하지 않는다. 기술 종속 처리는 어댑터와 실행 경계에 둔다.
- **EM-ARCH-02** *(필수)* — 업무 오류는 그 조건을 판단하는 위치에서 명시한다. 공통 필터는 알려진 의미를 변환하며, 알 수 없는 업무 의미를 추측하지 않는다.
- **EM-ARCH-03** *(필수)* — 오류를 감쌀 때 원본 cause와 관련 맥락을 보존한다. 의미 있는 오류가 이미 있다면 다시 일반 오류로 바꾸지 않는다.
- **EM-ARCH-04** *(권장)* — 같은 실행 단위 안에서는 예상 가능한 실패의 전달 방식을 통일한다. 타입이 있는 예외 또는 Result 방식 중 하나를 기본으로 선택하고, 경계에서만 의도적으로 변환한다.
- **EM-ARCH-05** *(금지)* — 모든 함수에 catch·throw를 기계적으로 추가하거나, 모든 실패를 null·빈 배열·성공 응답으로 바꾸지 않는다. 정상적인 빈 결과와 조회 실패는 구분한다.

## 4. 오류 카탈로그 규격

### 4.1 카탈로그를 단일 원본으로 관리한다

- **EM-CAT-01** *(필수)* — 오류 코드는 임의 문자열이 아니라 카탈로그에 등록된 식별자를 사용한다. 예시는 `CONTRACT_ALREADY_SIGNED`, `CUSTOMER_PHONE_DUPLICATE`, `ASSIGNMENT_OVERLAP`이다.
- **EM-CAT-02** *(필수)* — 코드는 업무 의미를 기준으로 나눈다. 같은 원인은 재사용하고, 사용자나 클라이언트가 다르게 대응해야 하는 원인은 분리한다. 코드에 고객 ID, 날짜, 파일명, HTTP 숫자를 넣지 않는다.
- **EM-CAT-03** *(필수)* — 이미 배포한 코드의 의미를 바꾸거나 다른 의미로 재사용하지 않는다. 문구 개선은 가능하지만 공개 params의 의미·타입·필수 여부 변경과 함께 호환성을 검토한다.
- **EM-CAT-04** *(필수)* — 정적 카탈로그와 실행 시 사실을 구분한다. 현재 사용량, 충돌 일정, 처리 결과, 요청 ID는 실행 시 데이터이며 카탈로그에서 추측해 고정하지 않는다.

## 5. HTTP 오류 응답 계약

### 5.1 기본 프로필

- **EM-API-01** *(필수)* — 신규 JSON HTTP API의 애플리케이션 제어 범위에서 발생하는 오류 응답은 RFC 9457 기반 `application/problem+json`을 기본으로 한다. 기존 API는 호환성 계획을 세운 뒤 전환한다. 프록시·WAF·외부 API 응답이 이 형식을 보장한다고 가정하지 않는다.
- **EM-API-02** *(필수)* — 본 규격에서는 `type`, `title`, `status`, `detail`, `code`, `requestId`를 기본 필수 필드로 채택한다. 이것이 RFC에서 모두 필수라는 의미는 아니다.
- **EM-API-03** *(필수)* — RFC의 기본 유형 식별자는 `type`이다. `code`는 검증된 별칭으로 사용한다. 두 값이 충돌하면 프런트는 알려진 코드의 업무 동작을 실행하지 않고 계약 위반으로 처리한다.
- **EM-API-04** *(필수)* — 원 서버의 실제 HTTP 상태와 본문의 `status`를 일치시킨다. 메시지 문장을 파싱하지 않는다. 프런트는 알 수 없는 확장 필드를 무시할 수 있어야 한다.
### 5.2 응답 예시

- **EM-API-05** *(필수)* — 오류 객체와 params는 공개 허용 목록으로 새로 생성한다. 원본 예외의 spread, 임의 metadata 전달, stack·cause 직렬화를 금지한다.
- **EM-API-06** *(필수)* — 사용자·테넌트별 오류 응답은 기본적으로 `Cache-Control: no-store`를 사용한다. 캐시가 필요한 공개 오류 응답은 별도 설계를 기록하고, 언어별 표현을 캐시한다면 캐시 키도 언어를 구분한다.
- **EM-API-07** *(필수)* — 복구 정보는 제한된 action 식별자와 검증된 데이터로 구성한다. 서버가 보낸 임의 JavaScript·HTML·URL을 실행하거나 그대로 이동하지 않는다. 버튼 노출은 권한 확인을 대체하지 않는다.
### 5.3 HTTP 상태 선택 기준

- **EM-API-08** *(필수)* — 401에는 적용 가능한 `WWW-Authenticate` challenge를 제공한다. 408은 서버가 요청을 제때 수신하지 못한 경우이며, 외부 서비스 호출의 모든 시간 초과에 사용하는 상태가 아니다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)
- **EM-API-09** *(필수)* — 외부 제공자의 401·429·500을 우리 사용자에게 동일 상태로 그대로 전달하지 않는다. 외부 API 키 오류는 사용자 로그인 오류가 아니며, 제공자 전체 할당량 부족은 개별 사용자의 요청 과다와 다르다. 대기 시간을 확실히 알 때만 일관된 `Retry-After`와 안내를 제공한다. [429의 정의: RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html)

## 6. 입력 검증과 DB·외부 오류 변환

### 6.1 입력 검증

- **EM-VAL-01** *(필수)* — 프런트 검증은 즉각적인 안내를 위한 것이고 서버 검증을 대체하지 않는다. 동일 제약의 타입·범위·코드·문구 정의를 공유하거나 동등성을 테스트한다.
- **EM-VAL-02** *(필수)* — 여러 필드 오류를 구조화해 보존한다. API 필드 경로를 화면의 입력란에 명시적으로 매핑하고, 연결할 수 없는 오류는 폼 수준에서 표시한다.
- **EM-VAL-03** *(필수)* — 이 규격의 `errors[].pointer`는 요청 JSON 본문 기준 JSON Pointer로 정의한다. query·path·header 검증을 지원하는 프로젝트는 위치 필드를 별도로 문서화한다. 서버 내부 속성명을 UI 라벨로 그대로 노출하지 않는다.
- **EM-VAL-04** *(필수)* — 공통 검증 코드는 `REQUIRED`, `INVALID_FORMAT`, `OUT_OF_RANGE`처럼 재사용할 수 있다. 사용자 문구에는 해당 입력란의 실제 명칭을 사용한다. 모든 필드마다 별도 최상위 오류 코드를 만들 필요는 없다.
### 6.2 DB·외부 연동

- **EM-MAP-01** *(필수)* — 원본 DB·SDK 오류는 해당 어댑터에서 공식 오류 타입·코드·제약 정보로 분류한다. 업무 맥락을 아는 계층이 필요한 경우 더 구체적인 업무 오류로 변환한다.
- **EM-MAP-02** *(금지)* — 모든 unique 위반을 사용자 중복 입력으로, 모든 외래 키 위반을 삭제 제한으로 단정하지 않는다. 내부 생성 식별자 충돌이나 데이터 불변식 위반은 시스템 결함일 수 있다.
- **EM-MAP-03** *(필수)* — 사전 조회만으로 중복·동시성 안전성을 보장했다고 판단하지 않는다. 최종 저장 단계의 제약 위반도 동일한 업무 의미로 처리하고, 충돌 시 조회한 설명 정보가 현재 권한과 사실을 만족하는지 확인한다.
- **EM-MAP-04** *(필수)* — 외부 오류 분류에는 제공자 이름, 제공자 코드, 요청 작업, 응답 수신 여부, 처리 결과의 확실성을 내부 정보로 보존한다. 공개 메시지는 사용자 업무 관점으로 다시 작성한다.

## 7. 처리 결과·재시도·비동기 작업

### 7.1 HTTP 실패와 업무 결과를 분리한다

- **EM-STATE-01** *(필수)* — 부수 효과가 있는 변경 작업은 오류 발생 시 실제 결과를 구분한다. HTTP 상태만으로 미처리·롤백·실패를 단정하지 않는다.
### 7.2 재시도 안전성

- **EM-RETRY-01** *(필수)* — 일시적인 원인인지, 재실행이 안전한지, 현재 상태를 확인했는지, 동일 작업을 식별할 수 있는지를 함께 판단한다. `retryable: true` 또는 5xx만으로 자동 재시도하지 않는다.
- **EM-RETRY-02** *(필수)* — 자동 재시도 허용 조건과 최대 횟수·총 시간·백오프·지터를 프로젝트 프로필에 명시한다. SDK, 서버, 프런트, 워커가 각각 중첩 재시도하지 않도록 최종 책임자를 정한다.
- **EM-RETRY-03** *(필수)* — 발송·결제·계약 생성 등 중복 부작용이 있는 작업은 멱등성 보장 또는 안전한 상태 확인 절차를 구현한다. 같은 논리 작업의 재시도는 같은 키와 같은 요청 의미를 유지하며, 다른 데이터에 같은 키를 재사용하지 않는다.
- **EM-RETRY-04** *(필수)* — 같은 키의 동시 요청, 처리 중 상태, 결과 저장 실패, 키 만료 이후 동작을 설계하고 테스트한다. 버튼 비활성화나 키 문자열 추가만으로 멱등성이 구현되었다고 판단하지 않는다.
- **EM-RETRY-05** *(필수)* — `UNKNOWN`에 대한 기본 action은 `CHECK_STATUS`이다. 안전성이 입증된 멱등 재시도는 예외적으로 허용할 수 있으나 사용자에게 미발송·미결제를 단정하지 않는다.
- **EM-RETRY-06** *(필수)* — 재시도 모드는 `NEVER`, `MANUAL`, `AUTOMATIC`으로 구분한다. `NEVER`는 같은 조건의 자동·반복 실행을 금지한다는 뜻이며, 사용자가 입력·권한·상태를 바꾼 새 시도까지 영구 금지한다는 뜻은 아니다.
### 7.3 부분 성공·워커·취소

- **EM-ASYNC-01** *(필수)* — 일부 성공한 복합 작업을 전체 실패로 표현해 전체 재실행을 유도하지 않는다. 예를 들어 고객 등록이 완료되었다면 문자 발송만 복구할 수 있도록 상태와 작업 경계를 분리한다.
- **EM-ASYNC-02** *(필수)* — 비동기 접수 성공을 최종 처리 성공이라고 표시하지 않는다. 접수 API와 작업 조회 API를 구분하고, 작업 ID로 상태·실패 원인·재시도 이력을 확인할 수 있게 한다.
- **EM-ASYNC-03** *(필수)* — 워커는 영구 실패, 재시도 중, 재시도 소진을 구분한다. 최종 실패는 사용자 작업 내역과 운영 관측에 연결하고, 자동 반복이 종료되지 않는 작업을 만들지 않는다.
- **EM-ASYNC-04** *(필수)* — 화면 이동에 따른 불필요한 조회 취소는 오류 토스트를 띄우지 않는다. 그러나 브라우저의 요청 중단을 서버 변경 작업의 취소 완료로 간주하지 않는다.

## 8. 프런트엔드 정규화와 표시 책임

### 8.1 API 클라이언트와 UI를 분리한다

- **EM-FE-01** *(필수)* — fetch·HTTP 라이브러리·Server Function의 오류를 공통 프런트 모델로 정규화한다. 각 화면이 제각각 응답 구조를 해석하지 않는다.
- **EM-FE-02** *(필수)* — TypeScript 타입 선언만 믿지 않고 런타임에서 응답을 검증한다. 본문 없음, HTML 오류 페이지, 잘못된 JSON, 미등록 코드, 잘못된 params, type·code 충돌을 처리한다.
- **EM-FE-03** *(필수)* — HTTP 상태와 오류 본문이 모순되면 임의로 유리한 값을 선택하지 않는다. 계약 위반으로 기록하고 안전한 안내를 사용한다. 프록시의 응답 변경 가능성도 보존한다.
### 8.2 문구 선택 순서

- **EM-FE-04** *(필수)* — Content-Type이 맞는다는 사실만으로 detail이 안전하다고 판단하지 않는다. 자체 API 출처, 스키마, 공개 필드 생성 정책이 전제되어야 한다. 외부 SDK의 원본 메시지나 `Error.message`를 이 fallback에 섞지 않는다.
- **EM-FE-05** *(필수)* — 최신 서버와 구버전 클라이언트 조합에서 오류 화면이 다시 오류를 일으키지 않아야 한다. 미등록 action은 숨기며 자동 재시도하지 않는다. 일반 안내로 축소된 이유는 관측한다.
- **EM-FE-06** *(필수)* — HTTP 클라이언트는 기본적으로 토스트를 띄우지 않는다. 화면 또는 합의된 표시 컨트롤러가 한 번만 표시한다. 공통 인터셉터와 개별 mutation에서 중복 안내하지 않는다.
- **EM-FE-07** *(필수)* — 변경 실패 시 사용자의 입력과 편집 맥락을 보존한다. 낙관적 UI를 사용하면 롤백 또는 서버 상태 재조회를 설계한다. 처리 결과 미확인 상태에서는 실제 서버 결과까지 실패했다고 단정해 덮어쓰지 않는다.
- **EM-FE-08** *(필수)* — 오류 경계만으로 버튼 클릭·비동기 요청 오류를 모두 처리한다고 가정하지 않는다. 이벤트와 작업 결과는 해당 실행 경로에서 명시적으로 처리한다. [Next.js 오류 경계의 범위](https://nextjs.org/docs/app/getting-started/error-handling)

## 9. 한국어·영어 UI 문구 작성 규칙

### 9.1 공통 문장 규칙

- **EM-COPY-01** *(필수)* — 사용자에게 표시하는 개별 오류의 핵심 설명은 한 문장으로 작성한다. 여러 입력 오류는 각 오류를 한 문장씩 보존하며, 모두를 하나의 토스트나 한 문장으로 합치지 않는다.
- **EM-COPY-02** *(필수)* — 사용자를 비난하지 않고 상태를 설명한다. “날짜를 잘못 입력하셨어요.”보다 “종료일이 시작일보다 빨라요.”를 사용한다.
- **EM-COPY-03** *(금지)* — 원인 없는 “오류가 발생했어요.”를 확인된 업무 실패의 기본 문구로 사용하지 않는다. 다만 원인을 알 수 없거나 공개하면 안 되는 경우는 정직한 일반 안내를 허용한다.
- **EM-COPY-04** *(금지)* — 모든 메시지에 사과, 감탄사, 이모지, 느낌표, 기술 용어를 넣지 않는다. “앗!”, “Oops!”, “Invalid request”, “Foreign key constraint failed” 같은 문구를 사용자 업무 안내로 그대로 사용하지 않는다.
- **EM-COPY-05** *(필수)* — 해결할 수 없는 행동을 요구하지 않는다. 재시도, 새로고침, 재로그인, 관리자 문의는 실제 문제 해결과 연결되고 안전할 때만 안내한다.
### 9.2 한국어는 해요체로 통일한다

- **EM-KO-01** *(필수)* — 오류 설명 본문은 `~해요`, `~없어요`, `~했어요`, `~해 주세요`로 작성한다. `~합니다`, `~하십시오`, `~하세요`, 명사형 단답을 섞지 않는다. 짧은 제목과 버튼은 “최신 내용 확인”, “다시 로그인”처럼 별도 라벨 규칙을 적용할 수 있다.
- **EM-KO-02** *(권장)* — 원인은 `~있어`, `~되어`, 대응은 `~으니`로 연결한다. “삭제가 불가해요” 같은 행정적·추상적 표현보다 구체적인 작업과 제한 사유를 사용한다.
- **EM-KO-03** *(필수)* — 조사와 어순을 고려한 완성 문장 템플릿을 사용한다. 임의의 명사를 붙여 `계약을`, `연락처를` 같은 조사가 깨지는 범용 문자열 조합을 만들지 않는다.
### 9.3 영어는 차분하고 직접적인 대화체로 통일한다

- **EM-EN-01** *(권장)* — 현재 규칙·상태의 제한에는 `can’t`, 시도 후 확인된 실패에는 `couldn’t`, 결과 불명확에는 `can’t confirm`을 기본 패턴으로 사용한다. 문법의 절대 규칙이 아니라 프로젝트의 의미 구분 규칙이다.
- **EM-EN-02** *(권장)* — 입력 안내는 `Enter`, `Select`, `Choose`, `Check`, `Review`처럼 행동 동사로 시작한다. 한국어의 “주세요”를 모든 문장에서 `Please`로 직역하지 않는다.
- **EM-EN-03** *(필수)* — 사용자 책임을 단정하지 않는다. `You entered an invalid date.`보다 `The end date is before the start date.`를 사용한다. 정확한 권한 안내에서 `You don’t have permission…`을 사용하는 것은 허용한다.
- **EM-EN-04** *(필수)* — 본문은 sentence case와 완전한 문장을 사용한다. 문장 연결을 위한 대시 문법은 사용하지 않는다. 과도한 수동태, 제목형 대문자, 로봇 같은 오류 코드 문장을 피한다.

## 11. 문구 소유권과 국제화

- **EM-I18N-01** *(필수)* — 기본 구조는 공유 가능한 공개 오류 계약과 중앙 문구 카탈로그다. 서버의 기본 detail과 프런트 문구를 서로 다른 원본으로 수동 관리하지 않는다. 같은 원본에서 생성하거나 동등성을 테스트한다.
- **EM-I18N-02** *(필수)* — 브라우저에 배포하는 공유 패키지에는 공개 스키마·코드·템플릿만 포함한다. 서버의 DB 제약 이름, 비공개 정책, 원본 예외 매핑표, 비밀 설정을 함께 번들링하지 않는다.
- **EM-I18N-03** *(필수)* — 한영 문구는 원인, 확실성, 처리 결과, 대응 행동이 일치해야 한다. “발송 여부를 확인할 수 없어요”를 `Failed to send`로 번역하지 않는다.
- **EM-I18N-04** *(필수)* — 지원 언어와 fallback 순서를 프로필에 명시한다. 기본 프로필은 `ko-KR`, `en-US`를 지원하며 `ko`·`en`을 각각 연결한다. 서버는 요청 언어를 협상하고 실제 언어를 `Content-Language`로 알린다. 다른 언어로 fallback했을 때 해당 사실을 클라이언트가 판단할 수 있어야 한다.
- **EM-I18N-05** *(필수)* — 숫자·날짜·시각·통화·용량은 원본 값과 단위를 전달한 뒤 공통 formatter로 표시한다. locale과 시간대는 별개다. 업무 날짜만 있는 값에 임의 시간대 변환을 적용해 날짜를 바꾸지 않는다.
- **EM-I18N-06** *(필수)* — 영어 단복수와 한국어 조사는 완성 문장 템플릿 또는 검증된 국제화 도구로 처리한다. UI에서 문장 조각을 이어 붙이지 않는다. [FormatJS ICU Message syntax](https://formatjs.github.io/docs/core-concepts/icu-syntax/)
- **EM-I18N-07** *(필수)* — 다국어 리소스 누락·placeholder 오류·번역 실패가 오류 처리 전체를 실패시키지 않게 한다. 안정적인 기본 문구로 복구하면서 계약·번역 결함을 기록한다. 런타임 LLM 번역으로 오류 이유를 새로 추측하거나 생성하지 않는다.

## 12. UI 위치·접근성·상호작용

- **EM-UI-01** *(필수)* — 토스트를 모든 오류의 유일한 표시 방식으로 사용하지 않는다. 중요한 실패·결과 미확인은 자동으로 사라지는 안내에만 의존하지 않는다.
- **EM-UI-02** *(필수)* — 오류는 텍스트로 설명하고 입력 항목과 프로그램적으로 연결한다. 색상만으로 구분하지 않으며, 필요한 `aria-invalid`·`aria-describedby`와 키보드 이동을 제공한다. [W3C 오류 식별](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)
- **EM-UI-03** *(필수)* — 제출 실패 시 오류 요약 또는 적절한 첫 오류에 일관되게 초점을 이동한다. 요약 항목은 해당 필드와 연결한다. 라이브 영역은 중요한 변경을 알리되 모든 입력마다 중복·과도하게 읽지 않도록 한다. [GOV.UK 오류 요약](https://design-system.service.gov.uk/components/error-summary/) · [W3C 상태 메시지](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **EM-UI-04** *(필수)* — 수정 방법을 알고 있고 보안상 문제가 없다면 안내한다. 권한 부족이나 서비스 장애를 잘못된 입력란 오류처럼 표시하지 않는다. [W3C 오류 수정 제안](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion)
- **EM-UI-05** *(필수)* — 한 문장 원칙 때문에 문장을 잘라내거나 말줄임표로 이유를 숨기지 않는다. 좁은 화면에서는 줄바꿈하고, 보조 정보와 버튼은 별도 영역에 둔다.
- **EM-UI-06** *(필수)* — 알 수 없는 오류에서도 사용자가 문의에 활용할 수 있는 참조 ID를 제공할 수 있어야 한다. 참조 ID는 기본 설명 문장과 분리하고, 내부 로그를 여는 공개 링크로 대체하지 않는다.

## 13. 내부 진단·Sentry·보안

### 13.1 기록해야 할 정보

- **EM-OBS-01** *(필수)* — 장애를 재구성하는 데 필요한 구조화 정보를 기록한다. 기본 항목은 `code`, 작업명, 실패 단계, 심각도, 발생 시각, 배포 버전, `requestId`, 가능한 경우 `traceId`, `operationId`, 원본 cause와 확인된 처리 결과다.
- **EM-OBS-02** *(필수)* — requestId는 개별 요청, operationId는 여러 요청·재시도를 아우르는 업무 작업, traceId는 분산 추적을 식별한다. Sentry event ID와도 구분하며 실제 존재하지 않는 ID를 UI에 만들지 않는다.
- **EM-OBS-03** *(필수)* — 동일 예외의 최종 보고 책임을 실행 경계별로 정한다. 서비스·컨트롤러·필터에서 같은 예외를 중복 capture하지 않는다. 분산 추적의 단계 정보와 서로 다른 시도의 기록까지 지우라는 뜻은 아니다. [OpenTelemetry 오류 기록](https://opentelemetry.io/docs/specs/semconv/general/recording-errors/)
- **EM-OBS-04** *(필수)* — 일반적인 입력 오류와 업무 거절은 지표·필요한 업무 기록으로 관찰하고, 시스템 결함·보안 이상·의존성 장애·결과 미확인은 별도 심각도 기준으로 경보한다. 예상 가능한 오류도 급증하면 조사한다.
- **EM-OBS-05** *(권장)* — 오류율뿐 아니라 코드별 빈도, 일반 fallback 사용률, 재시도 소진, 결과 미확인 지속 건수, 복구 성공률을 관찰한다. requestId나 고객 ID를 무제한 metric label로 사용하지 않는다.
### 13.2 정보 공개와 로그 보호

- **EM-SEC-01** *(필수)* — 개인정보와 비밀은 UI와 로그 모두에서 최소화한다. 토큰·비밀번호·쿠키·인증 헤더·원본 요청 본문·전체 상담 녹취를 일괄 수집하지 않는다. 진단에 필요한 필드만 허용하고 마스킹한다. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)
- **EM-SEC-02** *(필수)* — 브라우저에서 숨기는 것이 아니라 서버 응답 생성 전에 테넌트·역할·리소스 권한으로 공개 필드를 제한한다. 충돌 상대의 고객명·계약·일정 등은 조회 권한이 있을 때만 공개한다.
- **EM-SEC-03** *(필수)* — 계정 존재 여부나 다른 테넌트 리소스를 누설할 수 있는 상황에는 보안상 일반화된 안내를 사용한다. 로그인·비밀번호 복구 등은 문구뿐 아니라 상태 코드·응답 차이도 함께 검토한다. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- **EM-SEC-04** *(필수)* — 사용자 입력이 포함된 오류 문구는 텍스트로 렌더링한다. 임의 HTML과 실행 가능한 내용을 허용하지 않는다. 로그에도 줄바꿈·제어문자 등 입력을 안전하게 처리한다.
- **EM-SEC-05** *(필수)* — 로그·Sentry·작업 조회의 접근 권한과 보존 기간을 정한다. 로그 전송 실패가 원래 업무 오류를 덮어쓰거나 새로운 사용자 장애를 만들지 않게 한다.

## 15. 테스트와 병합 게이트

- **EM-QA-01** *(필수)* — 테스트는 코드와 상태만 확인하지 않고 데이터 변경 여부, 처리 결과, 사용자 문구, 복구 동작까지 확인한다.
- **EM-QA-02** *(필수)* — CI에서 등록 코드·번역 키·params 스키마의 대응을 검증한다. 공개 응답 fixture에 stack·token·비공개 필드가 포함되지 않는지 검사한다.
- **EM-QA-03** *(권장)* — 메시지 문자열 분기, raw `error.message` 출력, 도메인에서 HTTP·Sentry import, 중복 토스트 같은 패턴은 lint·아키텍처 규칙으로 탐지한다. 단순 문자열 검색 결과를 모두 결함으로 단정하지 않고 허용된 경계와 함께 검토한다.

## 16. 기존 프로젝트 도입 순서와 변경 관리

### 16.2 호환성 관리

- **EM-CHANGE-01** *(필수)* — 새 필드 추가와 새 코드 도입은 구버전 소비자가 안전하게 처리하는지 확인한다. 기존 코드의 의미 변경, type URI 변경, 필수 params 변경, 필드 경로 변경은 호환성 영향으로 검토한다.
- **EM-CHANGE-02** *(필수)* — 문구 변경은 업무 원인과 대응 의미를 보존한다. UI 문구 테스트를 변경할 때 실제 동작이 함께 바뀌어야 하는지 확인한다.
- **EM-CHANGE-03** *(필수)* — 메시지 비교에 의존하는 레거시 코드는 제거 대상으로 기록한다. 이행용 호환 로직은 지정한 어댑터에만 두고 제거 조건을 명시한다.
- **EM-CHANGE-04** *(필수)* — 새 오류 유형을 발견하면 일반 오류 문구를 늘리는 대신 원인 분석 후 카탈로그·매핑·한영 문구·회귀 테스트를 함께 갱신한다.
