## 데이터·운영 경계

- 사용자는 새 QA 전용 데이터 준비를 요청했고, 본인이 관리하는 전화번호와 이메일을 테스트 수신처로 제공했다.
- 실제 연락처는 대화에만 있으며 이 문서 및 Git 이력에 기록하지 않는다.
- 기존 고객·직원·계약 데이터는 QA 데이터로 간주하지 않는다.
- QA 생성·수정 전에 자동 문자, 예약 작업, 외부 전자문서 및 공개 지점 목록 영향을 확인한다.

- 코드 수정, 로컬 검증, CI, 병합, 배포, 프로덕션 재검수를 각각 기록한다.

## 완료 기준과 누락 관리

페이지 수만으로 기능 검수율을 계산하지 않는다. 각 화면의 버튼·메뉴·탭·필드·상태 전이를
개별 케이스로 등록하고, 코드에 있는 경로와 실제 렌더링된 조작 요소를 대조한다.

각 케이스에는 고유 ID, 역할/지점, 대상 버전, 장치/화면 크기, 사전 상태, 조작 단계,
예상 결과, 실제 결과, 증거, 결과 상태를 남긴다. 상태는 `미실행`, `통과`, `실패`,
`차단`, `해당 없음`으로 구분하며, 해당 없음에는 이유가 필요하다.

검사 축:

1. 정상 흐름: 생성 → 조회 → 수정 → 새로고침 → 다른 화면·PC/모바일에서 재조회.
2. 입력: 빈값, 공백, 경계 길이, 한글·특수문자, 전화·날짜, 중복, 잘못된 조합.
3. 상태: 로딩·빈 목록·오류·재시도·취소·뒤로가기·다중 탭·세션 만료.
4. 중복·경합: 연속 클릭 및 오래된 화면에서 저장. 격리된 QA 데이터에 한해 수행.
5. 발송: 수신처·내용 → 제공업체 처리 결과 → 앱 이력 → 실제 수신 확인.
6. 권한: 오너·지점장·직원·비로그인과 지점 간 경계. 오너 세션만으로 완료하지 않음.
7. UI: 정렬·간격·줄바꿈·잘림·대비·포커스·탭 순서·터치 영역·스크롤·팝업·모바일 키보드.
8. 수정 후 재발 방지: 재현 케이스와 연관 흐름, 실제 배포 후 같은 절차로 재확인.

전체 목록과 개별 상태 분기는 아직 수집 중이다. 미실행 및 차단 항목을 숨기거나,
한 번의 방문·성공 알림만으로 그 기능 전체를 통과 처리하지 않는다.

### MOBILE-002 재현 근거

- 같은 로그인 사용자, 화면에 표시된 같은 지점에서 PC와 모바일의 새 고객 등록 실행.
- 테스트 이름과 사용자가 지정한 기존 전화번호 입력. 새 고객은 저장하지 않음.
- PC: 중복 확인 중 → `이미 등록된 연락처 이에요.` 및 다음 버튼 비활성.
- 모바일: 확인 중 → `✓ 등록 가능한 번호입니다.`이나 다음 버튼은 여전히 비활성.
- 입력을 지우고 다시 타이핑하고 포커스를 이동해 동일 표시 재현.
- 브라우저에서 실제 발생한 모바일 GET `/api/clients/check-phone` 요청 관찰.
  `phone` query가 지정된 11자리 번호와 정확히 일치하는지 확인했으며, HTTP 200 응답은
  `{"exists":false}`였다. 요청 헤더·토큰·실제 번호는 기록하지 않는다.
- PC·모바일 양쪽 입력 폼을 취소하고 목록 복귀를 확인했다. 생성된 데이터 없음.
- 소스 확인: PC는 백엔드 전용 중복 확인 API를 호출하지만 모바일은 고객 목록을 받아 `phone` 필드를 순회한다.
  모바일 경로는 처리 실패도 HTTP 200 / `exists: false`로 반환한다. 두 구현은 배포 소스와 dev에서 동일하다.
- 원인: 모바일 BFF는 `limit: 500`을 요청하나 서버 목록 컨트롤러의 `parseInteger` 한도는 100이며,
  한도 초과 시 BadRequestException을 던진다. 해당 제한은 배포 소스에도 존재한다.
- 모바일 Vercel 운영 로그에서 2026-09-16 19:12:20 / 19:13:20 / 19:13:55 UTC의
  `/api/clients/check-phone` 처리 중 upstream 400 오류와 외부 HTTP 200 응답을 확인했다.
  백엔드 런타임 SHA와 내부 요청 로그는 별도로 확인하지 않았다.
- 모바일 다음 버튼 비활성은 원인 미확정이다. 입력 자동화와 제어된 전화 필드 간 상호작용 가능성도 남아 있어 별도 결함으로 확정하지 않는다.
- 저장소 스키마와 고객 서비스는 `(branchId, phoneNormalized)` 단위의 중복 검사를 정의한다.
  실제 운영 DB migration 적용 상태는 아직 확인하지 않았다.

### MESSAGE-001 실행 및 증거 경계

- 사용자가 지정한 수신처를 화면 값과 대조한 뒤 발송 버튼을 한 번 클릭했다.
- 본문: `[아가잼잼 QA 검수 20260917-01]`로 시작하는 관리자 발송 검수 안내 78자.
- PC Vercel 운영 로그에서 2026-09-16 19:28:52 UTC POST `/api/message-deliveries/sms`의
  HTTP 400과 `{ status: 400, code: 'REQUEST_INVALID', name: 'AxiosError' }`를 확인했다.
  브라우저의 해당 응답 본문과 제공업체 호출 여부는 아직 확보하지 못했다.
- 같은 화면을 다시 조회한 발송 이력 158건 응답에 검수 식별자가 없음을 확인했다.
- 실제 휴대전화 수신 여부를 사용자에게 질문했으며 현재 답변 대기 중이다.
- 중복 발송을 피하기 위해 재전송하지 않았다. 계약서·알림톡·이메일은 발송하지 않았다.
- 원인 범위 추가 확인: 지정 번호는 현재 지점의 고객과 직원 양쪽에 표시되어 있다.
  배포된 `message-delivery.controller.ts`는 `clientId`/`employeeId` 없이 같은 번호가 두 종류에서
  동시에 검색되면 `REQUEST_INVALID`로 거절한다. 인사 템플릿 화면은 전화번호만 입력받았으며,
  `TemplateSendForm`은 고객을 선택한 경우에만 `clientId`를 보낸다. 이번 거절과 일치하는 코드 경로다.

## 남은 준비 및 재개 지점

1. PC·모바일·공개 링크·관리 기능의 배포 소스 목록 수집과 개별 케이스 확장.
2. QA 지점 준비 방식에 대한 사용자 응답 대기. 배포 소스의 `auth.service.ts`를 확인한 결과,
   비활성 지점은 오너도 선택할 수 없고 활성 지점은 공개 지점 API에 포함된다.
   공개 목록에는 5분 캐시가 있다. 지점 생성 서비스의 기본 경로는 지점 저장과 감사 기록이며,
   관리자 미지정 시 관리자 배정은 하지 않는다. QA 지점은 비활성으로 생성했으며 활성화 방식은 응답 대기 중이다.
3. 안전한 QA 고객·직원·계약 fixtures 생성 후 고객 CRUD부터 실행.
4. 다른 역할의 검수 계정, 외부 발송과 실제 수신 확인, 백엔드 배포 식별.
