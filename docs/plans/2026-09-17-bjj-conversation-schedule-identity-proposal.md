# Phase7: proposed immutable schedule identity (approval required)

Status: user approved this exact local implementation and isolated synthetic DB verification on 2026-09-17. Independent SOL PLAN correction APPROVE/HIGH. Operational migration, merge, deployment and activation remain outside approval.

## Problem and proposed scope

The accepted task requires a deleted/recreated resource to be unable to inherit earlier SMS consent. `employee_schedule` currently has only a numeric ID and mutable business fields. No existing universally present immutable creation token was found. A UUID in the optional service-record assignment does not cover every schedule. A fingerprint of current fields cannot distinguish two successive rows with the same numeric ID and equal values.

Add one server-owned UUID to each schedule. It is generated by PostgreSQL on insertion, assigned once to existing rows by the additive migration, excluded from public write DTOs, and immutable afterward. Existing numeric IDs and relations remain unchanged. The private automation authority and dispatch check compare this UUID's digest. Ordinary schedule edits retain it; deleting and recreating the row generates a new one.

## Exact proposed schema change

In `backend/prisma/schema.prisma`, inside `model employee_schedule`:

```prisma
incarnationId String @unique @default(dbgenerated("gen_random_uuid()")) @map("incarnation_id") @db.Uuid
```

One new additive migration, proposed directory `backend/prisma/migrations/20260917000000_add_schedule_incarnation_identity/`, containing:

```sql
ALTER TABLE "employee_schedule"
  ADD COLUMN "incarnation_id" UUID NOT NULL DEFAULT gen_random_uuid();

CREATE UNIQUE INDEX "employee_schedule_incarnation_id_key"
  ON "employee_schedule" ("incarnation_id");

CREATE FUNCTION "reject_employee_schedule_incarnation_change"()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW."incarnation_id" IS DISTINCT FROM OLD."incarnation_id" THEN
    RAISE EXCEPTION 'Schedule incarnation identity is immutable';
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER "employee_schedule_incarnation_immutable"
  BEFORE UPDATE OF "incarnation_id" ON "employee_schedule"
  FOR EACH ROW EXECUTE FUNCTION "reject_employee_schedule_incarnation_change"();
```

`gen_random_uuid()` is already used by this repository's migrations. No extension, dependency, environment variable, or authentication change is proposed. The migration takes a table lock and assigns UUIDs to existing rows; operational timing must be reviewed separately before any deployment.

## Private authority binding

An affected automation scope is the tuple `branchId/clientId/clientCreationIdentity/kind/ruleId/scheduleId/scheduleIdentity/recipientType`. `scheduleIdentity` is null for client-only effects; otherwise it is the canonical SHA-256 binding of `{version:1, resource:"employee_schedule", incarnationId}`. This digest does not authorize delivery by itself.

Provenance lookup first uses the identity-free lineage key `branchId/clientId/kind/ruleId/scheduleId/recipientType`. Existing provenance with a different creation identity is refused, never reinterpreted as legacy. Whole-question consent still binds every reviewed effect and policy. Only changed scopes get new authority records under the branch lock; unchanged rule/recipient scopes retain their independent prior authority.
