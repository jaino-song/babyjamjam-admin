# Backup evidence contract (Phase 1A)

These inert, framework-free functions describe evidence for later adapters. They do not collect, store, export, back up, schedule, authorize or prove durable storage. No runtime consumer is connected in this phase. Phase 1B must persist acquisition/bundle/collection receipts and connect the collector after its own schema, migration and database verification.

## Identity compatibility v1

Hash input is UTF-8 of the exact domain label, one LF, then canonical JSON (no trailing LF). SHA-256 output and accepted content digests are exactly 64 lowercase hexadecimal characters; uppercase is rejected rather than normalized. Frozen labels are `eformsign-backup/artifact/v1`, `eformsign-backup/metadata/v1`, `eformsign-backup/bundle/v1`, and `eformsign-backup/document-id-set/v1`. Changing a label, selected metadata policy, artifact kind, serialization rule or required artifact set requires an explicit compatibility/version decision and new golden fixtures. Tests contain exact digests calculated independently with Python hashlib and sorted compact JSON, not calculated from production functions at assertion time.

Canonical JSON sorts object keys recursively by JavaScript UTF-16 ordering, retains array order, and uses JSON string escaping. Only null, booleans, Unicode scalar strings, safe integers (including negative metadata integers but excluding negative zero), plain Object-prototype objects and dense ordinary arrays are accepted. Floats, unsafe integers, undefined, nonfinite numbers, bigint, functions, symbols, symbol/hidden keys, accessors, sparse/extended arrays, cycles, proxies, custom prototypes and `__proto__`/`constructor`/`prototype` keys are rejected. Depth is capped at 64, nodes at 100,000, encoded bytes at 1 MiB. This is a conservative versioned profile, not general JSON/JCS compatibility. Identifiers are 1–256 ASCII characters matching `[A-Za-z0-9][A-Za-z0-9_.:-]*`; no whitespace, slash, control characters or implicit Unicode normalization. Counts and byte lengths are nonnegative safe integers. Failures expose only `Invalid evidence`, never input values.

An artifact ID hashes exactly `{companyId, documentId, artifactKind, contentSha256}`. Byte length is validated but is not identity. Acquisition ID/time and provider updated date are provenance, not immutable source revisions. Pass acquisition provenance separately; never add attempts, log payloads or raw provider errors to selected metadata. Callers explicitly select stable metadata fields before `metadataRevision`; the core cannot infer which provider fields are stable. Use a consistent selection policy across adapters.

A bundle requires document PDF (`document`) and audit PDF (`audit-trail`) from the same company/document context. Identical duplicate claims deduplicate; differing digests or lengths for the same kind are conflict. Missing artifacts are incomplete. Bundle identity hashes company/document context, artifact refs sorted by kind, metadataRevision and null sourceRevision. Changed required bytes or selected metadata change the bundle; artifact order and reacquisition do not. No provider immutable revision/atomic pair proof is currently qualified: even a fully present pair is **unverified**, never backup-complete or source-verified. Matching timestamps or hashes cannot upgrade it. Extra fields are not a proof input.

## Collection receipts

`evaluateCollectionReceipt` consumes supplied receipts, returning only fixed reason flags and observational completion. Both passes for all list types 01/03/04 are required (04 is management inbox). Each scan starts at ordinal/offset zero; subsequent actual page starts advance by the prior returned count. Every page needs a bounded returned count (at most its positive requested limit), constant total, outcome and persistence acknowledgement. The last page must be explicitly terminal and cumulative returned count must equal its total and the scan distinct-ID count. Earlier pages cannot already reach total or make zero progress. An explicitly empty terminal page is valid. A total-change explanation is diagnostic only: a changing total remains incomplete. Repeated passes must match distinct count and canonical sorted distinct-ID SHA-256 digest. `documentIdSetDigest` validates IDs but never returns them. Callers must supply correct aggregate digests; the evaluator cannot reconstruct sets from count-only pages.

Failed, interrupted, pending, missing and malformed evidence fails closed. Start, every page and final persistence acknowledgements must all be healthy. These acknowledgements are **evidence assertions supplied by an adapter**; this pure evaluator cannot prove durability or that the adapter really persisted anything. The adapter must await the correct successful writes and persist failures independently. Raw IDs, secrets and provider errors must never enter receipt/log output; only fixed flags/counts/digests belong there. Unknown extra JSON fields are ignored by the assessment and never copied to its output.

Even successful repeated scans remain company-coverage **unverified**. A declared company-wide visibility scope does not establish provider snapshot consistency, immutable source generations or archive durability. The current backfill callback has a mismatch with this contract: `skip` reports the next offset after a page, and the second pass exposes no page callback. Phase 1B must extend that callback with explicit pass, page ordinal, actual page-start offset and terminal evidence, and persist both passes. It must not reinterpret existing nextSkip as the page start. No existing backfill/mirror behavior changes in Phase 1A.

## Phase 1B source-only draft (inactive)

The additive run/page schema, repository and awaited collection writer are a reviewable draft. Neither writer nor repository is registered in the runtime module. An optional usecase dependency (or an explicit observer binding) exercises the lifecycle in tests. Scheduler and operator CLI supply the singular configured company ID, trigger and lock mode on both locked and approved-unlocked paths. No flag activates the draft. Generated migration, real PostgreSQL validation, independent final review and a separately reviewed registration change are required before activation. The ledger tables are created by migration `20261017161431_add_eformsign_backup_collection_ledger` (wired into the database-patches workflow with a fail-closed verify script); runtime registration is still absent.

Runs are global/system evidence, with no branch/tenant/document foreign key. Missing company configuration remains null and incomplete. Page keys are run/type/pass/ordinal; failed fetch or malformed responses retain unknown counts and terminal as null. Six scan summaries carry observed distinct counts/digests, expected/persisted pages and fixed failure codes. Raw IDs are used only transiently for the existing collector's set and digest calculation. PDFs, provider errors, customer metadata and credentials are never ledger payloads.

The separate observer is awaited before business mirroring and after both passes. Existing synchronous onProgress keeps its next-offset semantics. Credential failure is inside the receipt lifecycle; observation failures preserve the business result or original exception. Continuation/lease is checked after observer waits. The writer serializes per-run operations and latches failed persistence. The adapter also locks the started run row and compares duplicate page payloads before accepting their key. Interactive transactions have maxWait=1000ms and timeout=2000ms, including finalization; no Promise.race is treated as cancellation. These deadlines and rollback behavior still require real-DB proof.

Persisted assessment is deliberately a precommit candidate with observedScan=incomplete. The synchronous caller can receive complete only after final transaction commit resolves and all start/page/summary evidence is healthy. There is no committed-reread assessor yet: reading a completed outcome alone must never be interpreted as an acknowledged complete assessment. A crashed started run, failed write or ambiguous acknowledgement remains incomplete. Company coverage always stays unverified. The opt-in real-DB spec is skipped without HOLIDAY_REVIEW_REAL_DB=1 and refuses missing, mismatched or non-local/non-throwaway database targets.

Provider request list `type=01/03/04` and returned `status_type` are different fields. Existing internal treatment of 04 is preserved; vendor list enum semantics and company-wide visibility remain unverified. Repeated ID sets prove neither an atomic provider snapshot nor backup durability.

Rollback of a future activated version means removing the writer binding and returning to the prior collector code while retaining the additive ledger tables and evidence. Do not drop ledger data as an application rollback. Migration replay, constraints, timeout/rollback, crash recovery, forward reactivation and rollback must be verified on an authorized disposable PostgreSQL/shadow environment before phase close. Source-only tests are not those DB gates.
