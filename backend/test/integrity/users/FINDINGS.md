## Fix notes

### SI-USER-01 (high) — SENSITIVE (auth/approval core logic)
Smallest correct fix: inside the `reject` transaction, after reading `target`, refuse a non-pending state instead of rewriting it:
`if (target.approvalStatus !== "pending") throw new ConflictException(problemBody("REQUEST_CONFLICT", … "가입 심사 중이 아닌 계정은 거절할 수 없어요."))`.
No schema change needed (the state machine lives in `UserService.reject`). Flagged SENSITIVE because it changes the approval authorization path. Rollback: remove the precondition (single hunk in `backend/application/services/user.service.ts`).
If an "offboard an approved account" flow is wanted, it needs a separate explicit deactivate path (separate decision).

### SI-USER-02 (high) — SENSITIVE (auth/approval core logic)
Smallest correct fix: same precondition shape in `approve` — read the target's current `approvalStatus` first (the transaction currently never reads it) and throw `ConflictException` for anything non-pending; and write the audit `before` payload from the ACTUAL pre-read (`target.approvalStatus`, `target.role`) instead of the hardcoded `{ role: null, approvalStatus: "pending" }`. No schema change. Flagged SENSITIVE for the same reason. Rollback: single hunk revert.

### SI-USER-08 (medium) — not SENSITIVE (no schema/deps/approval-core changes)
Smallest correct fix: invalidate the cached authority when a protected call is refused because of an identity change, in both shells:
- Desktop: in `frontend/src/lib/api/client.ts`'s response interceptor, reject-with-reset for a 403 that carries `code: "ACCESS_DENIED"` (Problem-contract body, like `isAppAuthRequiredError`): acquire the shared `getQueryClient()` (or route through `resetAuthorityState`), then `invalidateQueries(AUTH_USER_QUERY_KEY)` so the next render re-fetches `/auth/me`; keep the error propagating to the caller. Avoid the `window.location.href` login redirect for a 403 (the session is still valid).
- Mobile: same in `mobile/src/lib/api/authenticated-fetch.ts`/`session-refresh.ts` — on 403 `getQueryClient().invalidateQueries(AUTH_USER_QUERY_KEY)`.
Server-side refusal stays authoritative either way; this only shrinks the stale-UI window from ≤30 min to one refetch.

### Residual observations (not defects, no ids)
- The second owner deletion in the SI-USER-06 race rejects with a raw `40001 could not serialize access` from the `lockRow` `$queryRaw`, because `runSerializableTransaction` retries only `P2034` (application/services/user.service.ts:1382-1387). Raw-query serialization aborts therefore surface as an internal error instead of the graceful 409. It fails CLOSED (no row touched, exactly one owner survived in the run), so it is not an integrity breach — a robustness fix would extend `isPrismaTransactionWriteConflict` to also match raw 40001s.
- After branch deactivation the member/owner sessions remain alive and refreshable (branchless). This is coherent because the user may legitimately hold other branches, and every branch-claim is re-derived per request; noted for future "deactivate + force branch re-selection" UX decisions.
