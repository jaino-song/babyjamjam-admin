## Historical fix proposals (final dispositions above)

- **SI-EMP-01** — compute the guard boundary the same way `findWorkHistoryByEmployee` does: `new Date(\`${isoDateInKorea()}T00:00:00.000Z\`)` in `SbEmployeeRepository.hasActiveAssignments` (and the sibling `findActiveClientsByEmployee`/`findAll`/`findByRegisteredDate*` local-midnight uses if their data is DATE-based: Postgres truncation of local-midnight timestamptz is the same off-by-one there). Not SENSITIVE.
- **SI-EMP-02** — either filter `deletedAt: null` in `SbEmployeeRepository.findById` (with a dedicated include-deleted lookup for the phone-uniqueness path that relies on `findByPhone`) or have `repository.update`/`changeOpenToNextWork` throw a `NotFoundException` instead of the bare `Error("Employee not found for branch")`. The usecases must then surface the 404-class error for a deleted employee. Not SENSITIVE.
- **SI-EMP-03** — add `smsAutomationEnabled` to the `IEmployeeRepository.updateIfTargetVersion` `updates` param type and pass it as the 7th `updateProfile` argument (or have the usecase strip and explicitly reject the flag on the approved path). One put-add on the agent zod `UpdateEmployeeSchema` in `employee-write-agent-capabilities.provider.ts` would be the minimal production-facing variant — deliberate because today only the schema addition makes the repository drop reachable. Not SENSITIVE.
- **SI-EMP-04 (delete half) / SI-EMP-09** — cancel/resync employee assignment jobs after deletion AND skip employees with `deletedAt != null` in `buildEmployeeAssignmentMessageRecipe`, so resync cannot re-arm tombstones. Keep the send-time gate unchanged: it already prevents delivery; this fix only removes stale pending rows. The openToNextWork/sms-disable halves need no fix. Do not add an SMS-disable recipe gate: mutation M-04b shows that would cancel the row that re-enabling must resume. Not SENSITIVE.
- **SI-EMP-05** — the app-level policy is the only guard; consider hardening the DB: a CHECK constraint `end_date >= start_date` on `employee_schedule` and making `branch_id NOT NULL` (every current writer stamps it). **SENSITIVE** (requires `backend/prisma/schema.prisma` + a migration; the NOT NULL part needs a backfill/verification that no historical NULL-branch rows must survive).
- **SI-EMP-06/07** — no fix needed; keep the `PrismaService` injection mandatory in production wiring (it is the guard carrier today).
- **SI-EMP-08** — make `employee_schedule` (and ideally `service_record_assignment`/assignment-relevant entities) also announce the `employee` realtime kind (desktop + mobile both already map `employee` → `["employees"]` roots), or add `["employees"]` to the `service-record` kind roots. Not SENSITIVE. The mobile DTO parity gap is one optional field on the mobile `Employee`/`UpdateEmployeeDto` types plus the toggle UI.
