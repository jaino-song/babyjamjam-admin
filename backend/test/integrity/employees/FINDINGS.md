Severity rationale: SI-EMP-02 is high because a soft-deleted employee stays readable and every management write on it is a 500 (an apache/Nest 500-path), i.e. a real API contract break reachable from the normal admin UI after a delete. SI-EMP-01/03/04/09 misjudge or leak state in bounded ways (delete refusal for ~9h/day in non-KST processes is the SI-EMP-01 user impact; pending SMS rows are blocked at dispatch time by `SmsAutomationSafeguardService`, which is why those are not critical). SI-EMP-08 is stale-UI that self-heals within the staleness window (10 min list / navigation refetches) — low.

## Fix notes

- **SI-EMP-01** — compute the guard boundary the same way `findWorkHistoryByEmployee` does: `new Date(\`${isoDateInKorea()}T00:00:00.000Z\`)` in `SbEmployeeRepository.hasActiveAssignments` (and the sibling `findActiveClientsByEmployee`/`findAll`/`findByRegisteredDate*` local-midnight uses if their data is DATE-based). Not SENSITIVE.
- **SI-EMP-02** — either filter `deletedAt: null` in `SbEmployeeRepository.findById` (with a dedicated include-deleted lookup for the phone-uniqueness path that relies on `findByPhone`) or have `repository.update`/`changeOpenToNextWork` throw a `NotFoundException` instead of the bare `Error("Employee not found for branch")`. The usecases must then surface the 404-class error for a deleted employee. Not SENSITIVE.
- **SI-EMP-03** — add `smsAutomationEnabled` to the `IEmployeeRepository.updateIfTargetVersion` `updates` param type and pass it as the 7th `updateProfile` argument (or have the usecase strip and explicitly reject the flag on the approved path). Not SENSITIVE.
- **SI-EMP-04** — call `refreshEmployeeAssignmentJobs` (or an equivalent) after `EmployeeService.delete` and after `smsAutomationEnabled`/`openToNextWork` changes, not only on name/phone. **SI-EMP-09** is the same fix's second half: the recipe/materialization layer must skip employees with `deletedAt != null` or `smsAutomationEnabled == false` (and arguably `openToNextWork == false` for NEW assignments) instead of only requiring a phone. Not SENSITIVE.
- **SI-EMP-05** — the app-level policy is the only guard; consider hardening the DB: a CHECK constraint `end_date >= start_date` on `employee_schedule` and making `branch_id NOT NULL` (every current writer stamps it). **SENSITIVE** (requires `backend/prisma/schema.prisma` + a migration; the NOT NULL part needs a backfill/verification that no historical NULL-branch rows must survive).
- **SI-EMP-06/07** — no fix needed; keep the `PrismaService` injection mandatory in production wiring (it is the guard carrier today).
- **SI-EMP-08** — make `employee_schedule` (and ideally `service_record_assignment`/assignment-relevant entities) also announce the `employee` realtime kind (desktop + mobile both already map `employee` → `["employees"]` roots), or add `["employees"]` to the `service-record` kind roots. Not SENSITIVE. The mobile DTO parity gap is one optional field on the mobile `Employee`/`UpdateEmployeeDto` types plus the toggle UI.
