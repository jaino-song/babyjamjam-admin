## Fix notes

### SI-CONTRACT-07 (CONFIRMED, low — storage hygiene)
Smallest correct fix: canonicalize the stored codes on any write that touches `eformsign_doc.status_type` (normalize at the repository entry like the completed-alias fences already do) or add a normalization backfill + `CHECK` in a migration once aliases are gone. Either is enough alone; the check is the durable guarantee. **SENSITIVE** (requires `backend/prisma/schema.prisma`/migration for the CHECK variant).

### SI-CONTRACT-08 (CONFIRMED, medium — stale client views)
Smallest correct fix: add `["clients"]` to the `document` roots in BOTH `frontend/src/lib/realtime/entity-query-keys.ts` and `mobile/src/lib/realtime/entity-query-keys.ts` (each map has a sibling test file that pins roots to real factories — extend it in the same change). Desktop contracts-page mutations that change contract state should also invalidate `clientKeys.all`/`clientKeys.detail(clientId)` alongside their `["eformsign-documents"]` invalidation. Not SENSITIVE (frontend/mobile only).

### SI-CONTRACT-09 (CONFIRMED, high — fence bypass on alias rows)
Smallest correct fix: normalize the stored status before the fence comparison in `UpdateEformsignDocStatusUsecase.executeWithOutcome` (e.g. `TERMINAL_STATUS_CODES.has(normalizeEformsignStatusCode(existing.statusType))` — `normalizeEformsignStatusCode` maps "50"→"050" and "doc_complete"→"003"), so the completed-alias row keeps the same protection the canonical row has. No DDL required; by the time this lands, alias row hygiene via SI-CONTRACT-07 covers historical data. Not SENSITIVE (backend code only, no schema/auth/package.json change).

### Cleanups observed, not counted as defects
- The `typeof fencedSync !== "function"` fallbacks (webhook `persist` closure, reconciler `persist` closure) are dead on the production wiring (SI-CONTRACT-03): low cleanup, delete the unfenced branch when convenient.
- `eformsign_dispatch_intent` reconciliation CHECK cannot reject `status='reconciled_delivered'` with `reconciled_outcome=NULL`: SQL CHECK passes a NULL-valued predicate. No application writer can produce that shape (status+outcome are written atomically in one UPDATE), so this is DB hardening trivia, not an exploit; the same CHECK does reject an explicit contradiction (covered by the dispatch-intent spec).
- `eformsign_webhook_event` has no unique on `webhook_id` by design (delivery ledger, one row per delivery); both deliveries are recorded while the side-effect dedupe lives in `claimCompletionStatus` — verified, no fix needed.
